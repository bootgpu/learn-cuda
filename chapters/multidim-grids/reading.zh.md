上一章处理的数据是一维数组：线程沿一个方向排开，每个线程用 `blockIdx.x * blockDim.x + threadIdx.x` 算出下标 `i`，处理第 `i` 个元素。然而许多数据不是一维的：图片由一行行、一列列像素组成，是二维的；视频是一帧接一帧的图片，是三维的。本章讨论数据为二维、三维时，线程应当如何排列，每个线程又如何找到自己负责的数据，并依次完成三个例子：把彩色图转换为灰度图、把图片变模糊、计算矩阵乘法。

## 把线程排成二维、三维

CUDA 的线程本身就可以按三维排列：一个 block 中的线程可以沿 x、y、z 三个方向排开，grid 中的 block 也是如此。x 为横向，y 为纵向，z 可以理解为一层层向后叠放。

以下图的 grid 为例。每个 block 横向 4 个线程、纵向 4 个、只有 1 层，按 x、y、z 的顺序记作 (4, 4, 1)；整个 grid 横向 3 个 block、纵向 2 个、也只有 1 层，记作 (3, 2, 1)。z 方向只有一层，所以这里的 block 和 grid 都是二维的。

::figure[3 × 2 个 block 组成的 grid，每个 block 4 × 4 个线程]{id="learn-cuda/grid-2d"}

启动配置中填写的正是这两组数：前一组是 grid，后一组是 block。每组三个数用类型 `dim3` 表示，通常先定义成变量，写在启动语句之前：

```cpp
dim3 grid(3, 2, 1);
dim3 block(4, 4, 1);
kernel<<<grid, block>>>(/* 参数 */);
```

几点说明：

- 某个方向只有一层时写 1，不能写 0。三个方向的数相乘才是线程数，写 0 意味着一个线程也没有，属于非法的启动配置，启动会失败。
- 省略的方向自动补为 1：`dim3 block(4, 4)` 等同于 `dim3 block(4, 4, 1)`。上一章启动配置中的单个整数同样如此，例如 `256` 会被转换为 `(256, 1, 1)`，只用到 x 方向，即一维的 block。
- block 的尺寸只给出一次，因此同一个 grid 中所有 block 的尺寸都相同。上图的 6 个 block 都是 4 × 4。

### 三个方向的内置变量

线程沿三个方向排列，内置变量也相应地具有 `.x`、`.y`、`.z` 三个分量：

| 变量        | 含义                        | 上图中圈出的线程 |
| ----------- | --------------------------- | ---------------- |
| `threadIdx` | 本线程在所属 block 中的编号 | (1, 2, 0)        |
| `blockIdx`  | 所属 block 在 grid 中的编号 | (2, 1, 0)        |
| `blockDim`  | block 的尺寸                | (4, 4, 1)        |

编号均从 0 开始。图中圈出的线程，在所属 block 中左侧有 1 个线程、上方有 2 个，所以 `threadIdx.x` 为 1、`threadIdx.y` 为 2；它所在的 block 左侧有 2 个 block、上方有 1 个，所以 `blockIdx.x` 为 2、`blockIdx.y` 为 1。只有一层，两者的 `.z` 均为 0。

使用几维，通常取决于数据的形状：数组是一维的，grid 和 block 都用一维；图片是二维的，二者都排成二维，计算下标最为直接。grid 与 block 的维数也不必相同。

## 每个线程处理哪个像素

以一张宽 10 像素、高 6 像素的小图为例，仍让每个线程处理一个像素。block 取 4 × 4，从图片左上角开始铺：横向一个 block 覆盖 4 列，两个覆盖 8 列，还差 2 列，所以横向需要 3 个 block；纵向一个 block 覆盖 4 行，还差 2 行，需要 2 个 block。这正是上一节 (3, 2, 1) 的 grid。

接下来确定每个线程负责的像素，也就是像素的**列号**（col）和**行号**（row），二者都从 0 开始计。看下图中圈出的线程：它所在 block 的 `blockIdx` 为 (1, 1)，它在 block 中的 `threadIdx` 为 (2, 1)。

- 列号：从左往右数，它前面有一整个 block，占去 4 列；在自己的 block 中再数过 2 个线程。列号为 `1 × 4 + 2 = 6`。
- 行号：从上往下数，前面有一整个 block，占去 4 行；在自己的 block 中再数过 1 个。行号为 `1 × 4 + 1 = 5`。

因此，该线程负责第 5 行、第 6 列的像素。

::figure[圈出的线程负责第 5 行、第 6 列的像素]{id="learn-cuda/thread-to-pixel"}

这与上一章计算 `i` 的方法完全相同：之前各 block 占去的位置，加上本线程在 block 中的位置。x 方向用于列号，y 方向用于行号：

```cpp
int col = blockIdx.x * blockDim.x + threadIdx.x;
int row = blockIdx.y * blockDim.y + threadIdx.y;
```

每个线程代入自己的编号，就得到自己负责的行号和列号。

### 两个方向的边界检查

整个 grid 横向 3 个 block，共 12 列线程；纵向 2 个 block，共 8 行线程。图片却只有 10 列、6 行，右侧多出 2 列线程，下方多出 2 行线程，它们算出的位置在图片之外。例如右上角的线程，列号为 11，而图片的列号最大为 9。

::figure[12 × 8 个线程覆盖 10 × 6 的图片，多出的线程落在图片之外]{id="learn-cuda/grid-overhang"}

上一章用 `if (i < n)` 排除多出的线程。二维时两个方向都可能越界，因此要同时检查两个条件：

```cpp
if (col < width && row < height) {
    // 处理第 row 行、第 col 列的像素
}
```

本例共启动 12 × 8 = 96 个线程，通过检查的恰好是 10 × 6 = 60 个，每个像素都由一个线程处理；其余 36 个线程不做任何操作。

## 启动配置：两个方向分别向上取整

host 端用两个 `dim3` 变量配置启动。block 的尺寸取固定值；grid 各方向的 block 数沿用上一章的向上取整，横向按宽计算，纵向按高计算：

```cpp
dim3 block(16, 16);
dim3 grid((width + block.x - 1) / block.x, (height + block.y - 1) / block.y);
kernel<<<grid, block>>>(/* 参数 */);
```

用前面的小图验证：block 取 4 × 4 时，横向 `(10 + 4 - 1) / 4 = 13 / 4 = 3`，纵向 `(6 + 4 - 1) / 4 = 9 / 4 = 2`，恰好是 (3, 2)。实际程序中 block 一般取 16 × 16，即 256 个线程。式子中写的是 `block.x`、`block.y` 而不是具体数字，改变 block 尺寸时无须修改。

变量名 `grid`、`block` 可以任意选取；kernel 中的 `threadIdx`、`blockIdx`、`blockDim` 则是 CUDA 规定的名称，不能更改。

:::warning
`dim3` 的第一个数是 x，即横向，对应的是**列**和图片的**宽**。这与「3 行 4 列」、`a[row][col]` 这类先行后列的习惯相反，很容易写反。仍以宽 10、高 6 的小图为例，grid 应为 (3, 2)；如果按先行后列的习惯写成 (2, 3)，横向只有 2 个 block、8 列线程，第 8、9 两列没有线程处理，结果出错。纵向多出的线程被 `if` 排除，程序不会报错，因此这类错误不易察觉。
:::

### block 与 grid 的尺寸上限

- 一个 block 的线程数，即三个方向之积，不能超过 1024。16 × 16 = 256 没有问题；32 × 32 = 1024 恰好达到上限。
- 各方向另有单独的上限：x 和 y 不超过 1024，z 不超过 64。
- grid 的上限宽松得多：x 方向最多 2³¹ − 1 个 block，y 和 z 方向各最多 65535 个，一般不会触及。

超过上限的启动配置会导致启动失败。如上一章「错误检查」一节所述，这类失败不会主动报告，需要在启动后调用 `cudaGetLastError()` 查询。

## 把二维数据摊平成一维

有了行号和列号，线程就要读取对应的像素。kernel 的参数 `in` 指向显存中的图片，最自然的写法是把它当作二维数组，写成 `in[row][col]`。但这样写无法通过编译。

原因在于内存是一维的：每个字节有一个地址，地址从 0 开始依次递增，只有一个方向。二维数组的元素在内存中也只能一个接一个地依次存放。写 `a[row][col]` 时，编译器要把它换算成从起点数起的第几个元素，换算时需要跳过前面的整行，因此必须知道一行有几个元素，而且在编译时就要知道：二维数组作为参数时，列数必须是常量，例如 `float a[][10]`。然而同一个 kernel 要处理各种尺寸的图片，宽度到运行时才通过参数传入。编译器无从得知一行的长度，这一换算只能由程序自己完成。

:::details[为什么不用指针数组]
C 语言中还有一种写法也能使用两个方括号：先分配一组指针，每个指针指向一行，`a[row]` 先取出第 `row` 行的指针，`[col]` 再在该行中定位。这种做法在 GPU 上代价很大：每一行都要单独调用一次 `cudaMalloc`，指针数组本身也要拷贝到显存；每读一个元素，还要先多读一次该行的指针。
:::

因此，通常的做法是在显存中只分配一整块连续的空间，把二维的元素依次排入，下标由程序自己计算。这称为**摊平**，也称**线性化**（linearization）。

### 行优先

最常见的摊平方式是一行接一行地存放：先放第 0 行，紧接着放第 1 行，依此类推，称为**行优先**（row-major）。以一个 3 行 4 列的矩阵为例，第 1 行、第 2 列的元素前面有一整行，占去 4 个位置，在本行中再数过 2 个，摊平后的下标为 `1 × 4 + 2 = 6`。这与计算列号的道理相同：之前整块占去的位置，加上块内的位置，只是这里的「整块」是一整行。

一行的元素个数就是矩阵的宽，因此行优先的下标为 `row * width + col`。前面无法编译的 `in[row][col]` 改写为：

```cpp
in[row * width + col]
```

### 列优先

也可以一列接一列地存放，称为**列优先**（column-major）。仍看第 1 行、第 2 列的元素：前面有两整列，每列 3 个元素，在本列中再数过 1 个，下标为 `2 × 3 + 1 = 7`。一列的元素个数是矩阵的高，因此列优先的下标为 `col * height + row`。

::figure[3 行 4 列的矩阵按行优先、列优先摊平，第 1 行第 2 列的元素分别位于下标 6 和 7]{id="learn-cuda/flatten-2d"}

C 和 C++ 的二维数组采用行优先。NVIDIA 的矩阵运算库 cuBLAS 则采用列优先，这是为了与 Fortran 程序兼容。两种存放方式混用时，如果没有对应好，就会取到错误的元素：同一个下标 7，按列优先是第 1 行、第 2 列，按行优先却是第 1 行、第 3 列。

### 由下标反推行号和列号

有时手中只有摊平后的下标，需要反过来求出行号和列号，例如线程按一维编号，处理的却是二维数据。按行优先存放时，下标 `i` 之前放满了若干整行，每行 `width` 个元素：

```cpp
int row = i / width;   // 前面放满了几整行
int col = i % width;   // 在本行中再数过几个
```

仍以 3 行 4 列的矩阵为例，下标 6 对应 `6 / 4 = 1`、`6 % 4 = 2`，即第 1 行、第 2 列，与前面的计算一致。按列优先存放时，每列 `height` 个元素，行与列的角色对调：`col = i / height`，`row = i % height`。下标 7 对应 `7 / 3 = 2`、`7 % 3 = 1`，即第 2 列、第 1 行。

### 三维数据

三维数据按同样的思路摊平。线程多出 z 方向的编号，称为**层号**（plane），计算方法与行号、列号相同，只是换成 `.z`：

```cpp
int plane = blockIdx.z * blockDim.z + threadIdx.z;
```

摊平时先放完第 0 层，再放第 1 层，每层内部按行优先存放。以 2 层、每层 3 行 4 列的数据为例：一层有 `3 × 4 = 12` 个元素，即宽 × 高。第 1 层、第 1 行、第 2 列的元素，前面有一整层，占去 12 个位置，再加上它在本层中的下标 6，摊平后的下标为 `12 + 6 = 18`。一般形式是在行优先的式子前再加一项：

```cpp
plane * width * height + row * width + col
```

::figure[2 层、每层 3 行 4 列的数据一层接一层摊平，第 1 层第 1 行第 2 列的元素位于下标 18]{id="learn-cuda/flatten-3d"}

三个方向都可能越界，因此边界检查要包含三个条件，host 端也要在三个方向上分别向上取整。设数据的层数（深度）为 `depth`：

```cpp
// kernel 中
if (col < width && row < height && plane < depth) {
    // 处理第 plane 层、第 row 行、第 col 列的元素
}

// host 端
dim3 block(8, 8, 4);
dim3 grid((width + block.x - 1) / block.x,
          (height + block.y - 1) / block.y,
          (depth + block.z - 1) / block.z);
```

这里 block 的 z 方向为 4，不超过 64；三个方向之积为 8 × 8 × 4 = 256，不超过 1024。

## 彩色图转灰度

前面几节分别说明了三件事：如何把线程排成二维，每个线程如何算出自己的行号和列号，以及如何把行号和列号换算成摊平后的下标。把三者组合起来，就可以写出第一个处理二维数据的 kernel：把彩色图转换为灰度图。

### 像素的存放方式

彩色图的每个像素由红（R）、绿（G）、蓝（B）三个**通道**（channel）组成，每个通道是 0 到 255 之间的整数，占 1 个字节（`unsigned char`），因此一个像素占 3 个字节。整张图按行优先摊平后，在内存中先是第一个像素的 R、G、B，紧接着是下一个像素的 R、G、B，如此交替排列。

灰度图的每个像素只有 1 个字节，表示亮度，计算公式为：

```
gray = 0.299 × r + 0.587 × g + 0.114 × b
```

三个系数中绿色的最大，因为人眼对绿色最为敏感。例如颜色为 (251, 148, 10) 的橙色像素，算得约 163.07，写入 `unsigned char` 时舍去小数部分，灰度为 163。各像素的计算相互独立，正好让每个线程处理一个像素。

### kernel

```cpp
#define CHANNELS 3

__global__ void rgbToGrayKernel(const unsigned char* in, unsigned char* out,
                                int width, int height) {
    int col = blockIdx.x * blockDim.x + threadIdx.x;
    int row = blockIdx.y * blockDim.y + threadIdx.y;
    if (col < width && row < height) {
        int i = row * width + col;
        unsigned char r = in[i * CHANNELS];
        unsigned char g = in[i * CHANNELS + 1];
        unsigned char b = in[i * CHANNELS + 2];
        out[i] = 0.299f * r + 0.587f * g + 0.114f * b;
    }
}
```

参数 `in` 是彩色图，`out` 是灰度图，`width` 和 `height` 是图片的宽和高。前两行算出列号和行号，`if` 排除图片之外的线程，随后算出摊平后的下标 `i`。灰度图每个像素占 1 个字节，下标 `i` 可以直接使用。彩色图每个像素占 3 个字节，第 `i` 个像素之前的 `i` 个像素共占 `i × 3` 个字节，所以它从第 `i × 3` 个字节开始，连续 3 个字节依次是 R、G、B。

以前面宽 10、高 6 的小图为例，负责第 5 行、第 6 列的线程算得 `i = 5 × 10 + 6 = 56`；在彩色图中，该像素从第 `56 × 3 = 168` 个字节开始，第 168、169、170 个字节依次是它的 R、G、B。

### host 端

host 端的启动配置与前面相同：

```cpp
dim3 block(16, 16);
dim3 grid((width + block.x - 1) / block.x, (height + block.y - 1) / block.y);
rgbToGrayKernel<<<grid, block>>>(d_in, d_out, width, height);
```

`d_in` 和 `d_out` 是指向显存的指针。实际图片的宽和高一般不是 16 的倍数，因此最右一列和最下一行的 block 都有一部分线程落在图片之外，由 `if` 排除。

## 把图片变模糊

在灰度转换中，每个线程只读取一个像素的 3 个字节，做几次乘加。下一个例子把图片变模糊，每个线程要读取周围一整块像素。

模糊使相邻像素之间的突变变得平缓：细节减弱，大的轮廓仍然保留。照片中常有零星的亮点或暗点，称为**噪点**。模糊之后，噪点与周围像素的差别变小，不再显眼，因此模糊常用于降噪。

### 均值模糊

最简单的模糊是取平均值：对输出图中的每个像素，在输入图的同一位置取出以它为中心的一块像素，例如 3 × 3 共 9 个，计算它们的平均值。

下面是一张灰度图左上角 5 行 5 列的像素值。第 2 行、第 2 列的 250 是一个亮噪点，周围的像素都在 50 上下：

```
 52  47  50  46  53
 55  52  55  50  49
 49  48 250  53  51
 51  51  49  54  50
 48  53  50  47  52
```

以 250 这个像素为中心的 3 × 3 块，是第 1 至 3 行、第 1 至 3 列的 9 个像素，总和为 662，除以 9 约为 73.56，舍去小数部分得 73。噪点从 250 降到了 73。它周围的 8 个像素，各自的 3 × 3 块中也都包含这个 250，输出值都是 72 或 73。原来孤立的一个亮点，变成了一片只比周围略亮的 3 × 3 区域，突变由此变得平缓。

:::details[加权平均]
均值模糊中，块内 9 个像素的地位相同。实际使用的模糊一般为每个像素设定**权重**，即它在平均中占几份，离中心越近，权重越大。例如中心占 4 份，上下左右各占 2 份，四角各占 1 份：每个像素乘以自己的权重后相加，再除以权重之和 16。这称为加权平均，常用的高斯模糊就属于这一类。像这样按权重对一块数据求和的计算称为**卷积**，「卷积滤波」一章专门讨论。
:::

### 模糊 kernel

仍然让每个线程计算一个输出像素：

```cpp
#define BLUR_SIZE 1  // 块的半径：块的边长为 2 * BLUR_SIZE + 1

__global__ void blurKernel(const unsigned char* in, unsigned char* out,
                           int width, int height) {
    int col = blockIdx.x * blockDim.x + threadIdx.x;
    int row = blockIdx.y * blockDim.y + threadIdx.y;
    if (col < width && row < height) {
        int sum = 0;
        int count = 0;
        for (int nRow = row - BLUR_SIZE; nRow <= row + BLUR_SIZE; ++nRow) {
            for (int nCol = col - BLUR_SIZE; nCol <= col + BLUR_SIZE; ++nCol) {
                if (nRow >= 0 && nRow < height && nCol >= 0 && nCol < width) {
                    sum += in[nRow * width + nCol];
                    ++count;
                }
            }
        }
        out[row * width + col] = sum / count;
    }
}
```

参数 `in` 是灰度图，每个像素 1 个字节，下标无须像彩色图那样乘以 3。开头算列号、行号和 `if` 的三行与灰度 kernel 完全相同。

块的大小由常量 `BLUR_SIZE` 决定，它是块的**半径**，即从中心向外延伸几格。半径为 1 时，向左、向右各延伸 1 格，加上中心一格，边长为 2 × 1 + 1 = 3，块为 3 × 3；半径为 2 时，块为 5 × 5。

新增的是中间的两层循环，逐个读取块内的像素。`nRow`、`nCol` 是正在读取的位置的行号和列号，以区别于线程自己负责的 `row`、`col`。外层循环让 `nRow` 从 `row - BLUR_SIZE` 取到 `row + BLUR_SIZE`，内层循环让 `nCol` 从 `col - BLUR_SIZE` 取到 `col + BLUR_SIZE`。以负责 250 那个像素的线程为例，`row` 和 `col` 都是 2，`nRow` 和 `nCol` 都依次取 1、2、3，共 9 个位置。每个位置按行优先算出下标 `nRow * width + nCol`，读出像素值累加到 `sum`，同时 `count` 加 1。循环结束时 `sum` 为 662、`count` 为 9；`sum / count` 是整数除法，舍去小数部分，得 73，写入输出图的同一位置。循环内的 `if` 和 `count` 的作用，下一小节说明。

另外两点：

- 输入和输出必须是两块不同的显存。每个线程都要读取周围像素的原值，如果把结果直接写回输入图，相邻的线程可能读到已被改写的值。
- 上一章把串行代码中的循环换成了一批线程，这里的 kernel 中又出现了循环。哪些循环应当换成线程，哪些应当留在线程内部，讲到矩阵乘法时再讨论。

host 端的启动配置与灰度 kernel 相同。

### 块越过图片边缘

中心像素位于图片边缘时，块会伸到图片之外。以左上角的像素为例，它的行号和列号都是 0，3 × 3 块覆盖第 −1 至 1 行、第 −1 至 1 列，其中有 5 个位置的行号或列号为 −1，不在图片中。

::figure[左上角像素的 3 × 3 块有 5 个位置落在图片之外]{id="learn-cuda/blur-edge"}

如果不加检查，直接按 `nRow * width + nCol` 读取，这些位置会读到错误的数据：

- 第 1 行、第 −1 列：下标为 `1 × width − 1`，即第 1 行起点的前一个元素。图片按行优先存放，这是第 0 行的最后一个像素，位于图片的另一侧，与当前像素并不相邻。
- 第 −1 行：下标为 `−1 × width + nCol`。`nCol` 小于 `width`，结果为负数，落在数组起点之前，属于越界访问。

因此，读取每个位置之前，都要先检查它是否在图片内，即循环内的 `if`：

```cpp
if (nRow >= 0 && nRow < height && nCol >= 0 && nCol < width)
```

与 kernel 开头的检查相比，这里多了两个「不小于 0」的条件。线程自己的 `row`、`col` 由非负的编号算出，不会小于 0；而 `nRow`、`nCol` 由 `row`、`col` 减去半径得到，可能为负数。

跳过图外的位置之后，各像素实际累加的个数就不同了：角上的像素只有 4 个位置在图内，边上不在角上的像素有 6 个，只有内部的像素才是完整的 9 个。如果一律除以 9，左上角像素的结果为 (52 + 47 + 55 + 52) / 9 = 206 / 9，得 22，远低于原值 52；边上的像素同样因为除数偏大而偏暗，整张图的四周会暗下去一圈。

正确的做法是实际累加了几个，就除以几。`++count` 写在 `if` 之内，图外的位置不计数，因此 `count` 恰好是实际累加的像素个数。左上角像素为 206 / 4，得 51，与原值 52 接近。中心像素本身一定在图片内，`count` 至少为 1，不会出现除以 0。

灰度 kernel 只在开头做一次检查；模糊 kernel 每读取一个像素，都要多做一次检查。由此得出一个通用的习惯：每次读写数组，都要确认下标在合法范围之内。

## 矩阵乘法

在模糊中，每个线程读取 9 个乃至更多像素。本章最后一个例子是矩阵乘法：每个线程要用一个矩阵的一整行，去乘另一个矩阵的一整列。

矩阵乘法在线性代数中几乎无处不在，许多求解方程和数值计算的算法都以它为基础；训练和运行神经网络时，大部分计算也是矩阵乘法。同一种运算，不同写法的速度可能相差几个数量级。本节先写最朴素的一种，更快的写法留到「更快的矩阵乘」一章。

:::details[BLAS 的三个级别]
线性代数中最常用的运算有一套标准的函数库接口，称为 BLAS（Basic Linear Algebra Subprograms）。「列优先」一节提到的 cuBLAS，就是 NVIDIA 在 GPU 上对它的实现。BLAS 按参与运算的是向量还是矩阵分为三级：第一级是向量与向量的运算，上一章的向量加法即属于这一级；第二级是矩阵乘向量；第三级是矩阵乘矩阵，也就是本节的例子。
:::

### 矩阵乘法计算什么

设 P = M × N。P 中第 `row` 行、第 `col` 列的元素，由 M 的第 `row` 行与 N 的第 `col` 列算出：两者从头开始，第一个元素乘第一个元素，第二个乘第二个，直到最后一个，再把这些乘积全部相加。这种运算称为**点积**。

点积要求两边的元素一一配对，因此 M 一行的元素个数必须等于 N 一列的元素个数，即 M 的列数等于 N 的行数。矩阵不必是方阵：例如 M 为 4 行 6 列、N 为 6 行 3 列，M 的一行与 N 的一列都是 6 个元素，可以相乘。M 的每一行对应 P 的一行，N 的每一列对应 P 的一列，因此 P 为 4 行 3 列，行数与 M 相同，列数与 N 相同。

为便于说明，本节只讨论方阵：M、N、P 都是 n 行 n 列。点积写成式子为：

```
P[row][col] = M[row][0] × N[0][col] + M[row][1] × N[1][col] + … + M[row][n−1] × N[n−1][col]
```

::figure[n = 6 时，P 第 1 行、第 4 列的元素由 M 的第 1 行与 N 的第 4 列做点积得到]{id="learn-cuda/matmul-dot"}

### 每个线程计算 P 的一个元素

P 有 n² 个元素，每个元素都要做一次点积，而且各个点积互不依赖。沿用前面的做法，让每个线程计算 P 的一个元素。每个线程的行号、列号与灰度 kernel 的算法相同；算出的 (`row`, `col`) 既确定了线程，也是它负责的元素在 P 中的位置。

以 n = 6 为例，block 取 3 × 3，grid 取 2 × 2，恰好覆盖 6 × 6 的 P。每个 block 负责 P 中的一个 3 × 3 区域，这样的区域称为 **tile**，P 被分成 4 个 tile。「共享内存与分块」一章还会用到这个概念。

```cpp
__global__ void matMulKernel(const float* M, const float* N, float* P, int n) {
    int col = blockIdx.x * blockDim.x + threadIdx.x;
    int row = blockIdx.y * blockDim.y + threadIdx.y;
    if (row < n && col < n) {
        float sum = 0.0f;
        for (int k = 0; k < n; ++k) {
            sum += M[row * n + k] * N[k * n + col];
        }
        P[row * n + col] = sum;
    }
}
```

开头算列号、行号和边界检查的三行与灰度 kernel 相同，只是宽和高都是 n。接下来是点积：`sum` 从 0 开始，`k` 从 0 取到 n − 1，每一步把 M 第 `row` 行的第 `k` 个元素与 N 第 `col` 列的第 `k` 个元素相乘，累加到 `sum`。循环结束后，把 `sum` 写入 P 的第 `row` 行、第 `col` 列。

三个矩阵都按行优先摊平，宽都是 n，下标都按「行号 × n + 列号」计算：

- M 中取的元素位于第 `row` 行、第 `k` 列，下标为 `row * n + k`。`k` 每增加 1，下标增加 1，依次读取内存中连续的 n 个元素。以 n = 6 时负责第 1 行、第 4 列的线程为例，下标依次为 6、7、8、9、10、11。
- N 中取的元素位于第 `k` 行、第 `col` 列，下标为 `k * n + col`。`k` 每增加 1，下标增加 n，每次跳过一整行。同一个线程在 N 中读取的下标依次为 4、10、16、22、28、34。
- P 的写入位置为 `row * n + col`，与灰度 kernel 中的 `row * width + col` 是同一个式子。

::figure[负责 P 第 1 行、第 4 列的线程在摊平的 M 中连续读取下标 6 至 11，在摊平的 N 中每次跳过 6 个元素]{id="learn-cuda/matmul-index"}

host 端的启动配置与灰度 kernel 相同，宽和高都换成 n：

```cpp
dim3 block(16, 16);
dim3 grid((n + block.x - 1) / block.x, (n + block.y - 1) / block.y);
matMulKernel<<<grid, block>>>(d_M, d_N, d_P, n);
```

### 哪些循环换成线程

模糊一节留下了一个问题：哪些循环应当换成线程，哪些应当留在线程内部。矩阵乘法在 CPU 上写成三层循环，正好用来回答：

```cpp
for (int row = 0; row < n; ++row)
    for (int col = 0; col < n; ++col) {
        float sum = 0.0f;
        for (int k = 0; k < n; ++k)
            sum += M[row * n + k] * N[k * n + col];
        P[row * n + col] = sum;
    }
```

外两层分别遍历行号和列号，每一轮计算 P 中不同的元素，各轮之间互不依赖，因此都换成了线程。上一章把整个循环换成一批线程，能这样换的，正是这种各轮互不依赖的循环。最内层则不同：每一轮都把乘积加到同一个 `sum` 上，要等上一轮加完才能进行，因此留在线程内部，按顺序执行。

最内层也并非不能拆开，但需要多个线程相互配合，共同累加出同一个和，这种计算称为**归约**，「把数组归约成一个值」一章专门讨论。模糊 kernel 的两层循环同样累加到同一个 `sum` 上，所以留在线程内部。灰度转换没有让三个线程分别处理三个通道，也是同样的道理：三个通道最终要合成同一个灰度值，因此由同一个线程计算。

## 换一种分工：一个线程算一整行

一个线程计算 P 的一个元素，并不是唯一的分工方式。上一章「一个线程计算多个元素」一节已经说明，一个线程也可以负责多个元素。对矩阵乘法，一种自然的做法是让一个线程计算 P 的一整行。

这时线程只需排成一维，共 n 个：第 `row` 个线程负责 P 的第 `row` 行，`row` 就是上一章的全局下标：

```cpp
int row = blockIdx.x * blockDim.x + threadIdx.x;
```

线程内部再用一个循环，依次走过这一行的每一列；每一列都是一次独立的点积，即前面 kernel 中的 `k` 循环。线程只沿一个方向排开，边界检查也只剩一个条件 `row < n`。

分工改变的只是每个线程负责哪些元素，元素本身的算法不变：P 第 `row` 行、第 `col` 列的元素，仍是 M 的第 `row` 行与 N 的第 `col` 列的点积，下标仍是 `row * n + k`、`k * n + col` 和 `row * n + col`。

同样的思路适用于每一行产生一个结果的计算。例如矩阵乘向量：结果的第 `row` 个元素是矩阵第 `row` 行与向量的点积，让一个线程负责一行，在线程内部循环走完这一行即可。矩阵不是方阵时要注意，一行的元素个数是矩阵的宽（列数），而线程数和边界检查用的是矩阵的高（行数）。

这种分工的代价是线程变少：线程数从 n² 降到 n，每个线程的工作量增加到 n 倍。GPU 依靠大量线程同时执行来获得速度，一块 GPU 可以同时运行数以万计的线程。n = 100 时，一个线程算一个元素需要 10000 个线程，一个线程算一行只有 100 个，GPU 的绝大部分计算资源都闲置。因此分工时，要让线程数足以填满 GPU；线程数取决于按什么来分，按行分等于行数，按列分等于列数。至于线程数相同时哪种分工更快，还与读取内存的方式有关，留到「kernel 性能调优」一章比较。

## 实测：矩阵乘法的耗时

上一章实测向量加法时，GPU 全流程的耗时与 CPU 相当，时间几乎全部用于数据传输，kernel 只占 0.5%。矩阵乘法的情况如何？我们同样在一块 H100 上做了实测：n = 2048，每个矩阵约 419 万个元素（16 MB）；CPU 单核运行上面的三层循环，GPU 完整执行五个步骤，kernel 即本节的 `matMulKernel`，block 取 16 × 16。GPU 预热一次后重复 7 次取中位数；CPU 每次约 45 秒，运行 3 次取中位数。

| 做法                 |    耗时 | 占 GPU 全流程 |
| -------------------- | ------: | ------------: |
| CPU 单核运行三层循环 |  44.8 s |             — |
| GPU 完整执行五个步骤 |  9.0 ms |          100% |
| ├ 拷贝到显存         | 3.62 ms |           40% |
| ├ 拷贝回内存         | 1.36 ms |           15% |
| ├ kernel 执行        | 3.20 ms |           36% |
| └ 分配与释放显存     | 0.70 ms |            8% |

CPU 与 GPU 的耗时相差约 5000 倍，但这个倍数说明不了多少：作比较的 CPU 只用了一个核，运行的也是未经优化的朴素循环，换用多核和优化过的数学库，CPU 会快得多。值得关注的是 GPU 一侧的时间构成：拷贝仍占一半以上，但 kernel 已占三分之一以上，而向量加法中 kernel 还不到 1%。

同样需要来回拷贝，差别来自数据量与计算量的比例。矩阵乘法要把 M、N 拷贝到显存，再把 P 拷回内存，三个矩阵各有 n² 个元素，数据量与 n² 成正比；计算量则是 P 的 n² 个元素各做 n 次乘加，共 n³ 次，比数据量多出一个因子 n。换个角度看：M 中的一个元素只拷贝一次，却要被负责 P 中同一行的 n 个线程各用一次，n = 2048 时，拷贝一次，使用 2048 次；而向量加法中，每个元素只用一次。每个元素拷贝一次后被使用的次数越多，拷贝所占的比例就越小。

实测结果与此相符：n = 1024 时，GPU 全流程耗时 1.91 ms，其中 kernel 0.45 ms，占 24%；n 增大到 2048，kernel 的占比升至 36%。每读取一个元素，至少要做多少次计算才不会被读取数据拖慢，「共享内存与分块」一章还会在 kernel 读取显存的层面讨论这个问题。

## 小结

本章回答了开头的问题：数据为二维、三维时，线程如何排列，每个线程又如何找到自己负责的数据。

1. 线程可以排成二维、三维：用 `dim3` 指定 grid 和 block 的尺寸，x 对应列，y 对应行，z 对应层。
2. 每个线程的列号、行号、层号都等于「block 编号 × block 尺寸 + 线程编号」，分别取 `.x`、`.y`、`.z` 分量。host 端在每个方向上分别向上取整，kernel 中对每个方向分别做边界检查。
3. 内存是一维的，多维数据要摊平。按行优先存放时，二维下标为 `row * width + col`，三维再加上 `plane * width * height`；由下标反推行号、列号用 `/` 和 `%`。
4. 灰度、模糊、矩阵乘法三个 kernel 都让一个线程计算一个输出元素，每个线程的工作依次加重。各轮互不依赖的循环可以换成线程，累加到同一个值上的循环留在线程内部。
5. 一个线程算一个元素并非唯一的分工。分工决定线程数，线程数要足以填满 GPU。

**CUDA 只提供线程的编号，编号与数据如何对应，由编写 kernel 的人决定。** 编号用错时，线程照样读写，只是拿到了错误的数据，程序往往不会报错。

本章没有讨论 block 的尺寸应当如何选取，也没有讨论这么多线程在硬件上如何执行，这些是「GPU 如何执行线程」一章的内容。
