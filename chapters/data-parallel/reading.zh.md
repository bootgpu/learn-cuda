## 什么样的计算能交给 GPU

GPU 不追求把一件事做得特别快，而是让一大批事同时做完。那什么样的计算，才能同时交给一大批线程去做呢？

打个比方：一百份卷子，一百个助教可以同时开工，因为每份卷子各改各的，改这一份用不着看别的卷子。程序里也有很多计算是这样的。最简单的例子是**向量加法**：两个长度都是 `n` 的数组 `a` 和 `b`，把同一个位置上的两个数相加，放进数组 `c` 的同一个位置。

```
c[i] = a[i] + b[i]
```

算 `c[i]` 只用到 `a[i]` 和 `b[i]`，跟别的位置毫无关系。所以这 `n` 个元素谁先算、谁后算都行，全部同时算也行。

像这样，每一份数据的计算互不依赖、可以同时进行，就叫**数据并行**。这样的计算到处都是：

- 调整一张照片的亮度：几百万个像素，每个像素各算各的。
- 模拟大量粒子的运动：每一步里，每个粒子的新位置各算各的。
- 把一百万个数加成一个总和：看上去只能一个接一个地累加，其实也能拆成很多小段，每段先各自求和，再把结果合起来（后面「把数组归约成一个值」一章专门讲）。

还有一种并行叫**任务并行**：几件不同的事同时做，比如播放器一边解码画面、一边播放声音。任务并行能有几份，取决于程序拆成了几件互不依赖的事，数据再多也不会变多。数据并行不一样：数据越多，能同时算的份数就越多，而且一行代码都不用多写。照片的长和宽各翻一倍，像素变成四倍，能同时干活的线程也跟着变成四倍。GPU 的性能主要就靠数据并行。

写数据并行的程序，就是围绕数据重新组织计算，把互不依赖的计算交给不同的线程同时去做。真实程序里的数据并行往往藏得更深，得先把它找出来，这门课大部分的功夫都花在练这个本事上。

## 从 for 循环到 kernel

先看最熟悉的写法：用普通的 C 语言，在 CPU 上做向量加法。

```cpp
void vecAdd(const float* a, const float* b, float* c, int n) {
    for (int i = 0; i < n; i++) {
        c[i] = a[i] + b[i];
    }
}
```

这是串行写法：一百万个元素，循环就要迭代一百万次，同一时刻只有一个元素在算。这样按顺序一条一条执行下去的指令流，就是一个**线程**。

### host 和 device

到了 CUDA 里，程序分成两边：CPU 这边叫 **host**，GPU 这边叫 **device**。两边的代码可以写在同一个源文件里（扩展名 `.cu`）。大部分代码还是普通的 C++，在 host 上跑；只有交给 GPU 的那部分，要用 CUDA 专用的关键字标出来。所以一个普通的 C++ 程序，可以看作一个只有 host 代码的 CUDA 程序。CUDA 只在 C++ 上加了少数几样新语法和库函数。

### kernel

交给 GPU 的那部分是一个函数，叫 **kernel**。kernel 在 GPU 上由一大批线程一起执行。把上面的串行函数改成 kernel，有两处改动：

```cpp
__global__ void vecAddKernel(const float* a, const float* b, float* c, int n) {
    int i = /* 这个线程该算第几个元素？下一节填 */;
    c[i] = a[i] + b[i];
}
```

1. 函数前面加关键字 `__global__`（前后各两个下划线），意思是：这是一个 kernel，从 host 调用，在 device 上执行。kernel 的返回类型必须是 `void`。
2. `for` 循环没了，函数体里只剩下算一个元素的那一行。

原来那 `n` 次迭代并没有凭空消失。启动 kernel 时，CUDA 一下子开出一大批线程，每个线程把函数体执行一遍，正好顶替原来的一次迭代。这种把循环的每次迭代拆给一个线程的做法，叫**循环并行**。所有线程跑的都是同一份代码，只是各自处理不同的数据，这种方式叫 **SPMD**（Single Program, Multiple Data，单程序、多数据）。每个线程自己，还是从上往下一句一句按顺序执行。

一个元素就开一个线程，开销会不会太大？在 CPU 上开一个线程确实不便宜；GPU 上线程的创建和调度都由硬件来做，非常便宜，一次开出几百万个线程是常事。

## 每个线程算哪个元素

所有线程跑同一份代码，而 `i` 每个线程都得不一样；否则大家都去算同一个元素，剩下的元素就没人算了。每个线程怎么知道自己该算第几个？

### grid、block 和线程

CUDA 的线程不是一个一个零散地开，而是分组：

- 每组叫一个 **block**。同一次启动里，每个 block 的线程数都一样多。一个 block 最多 1024 个线程，常用 256，最好是 32 的倍数（原因跟硬件怎么执行有关，「GPU 如何执行线程」一章再讲）。
- 一次启动的全部 block，合起来叫一个 **grid**。

每个线程都能读到几个 CUDA 预先设好的变量：

| 变量          | 含义                                                         |
| ------------- | ------------------------------------------------------------ |
| `threadIdx.x` | 线程编号：这个线程在自己 block 里的编号，从 0 开始           |
| `blockIdx.x`  | block 编号：这个线程所在的 block 的编号，同一 block 的线程读到的都一样 |
| `blockDim.x`  | 每个 block 的线程数                                          |

这些变量只能读，不能改。后缀 `.x` 是因为线程还可以排成二维、三维（下一章讲）；本章的数据是一维的，只用 `x`。

### 全局编号

拿一个小例子来算：每个 block 4 个线程，看 1 号 block 的 2 号线程。它前面的 0 号 block 有 4 个线程，已经占了 0 到 3 这四个位置，所以它的 `i` 是 `1 × 4 + 2 = 6`。

| block | 线程编号 | `i`        |
| ----- | -------- | ---------- |
| 0     | 0 1 2 3  | 0 1 2 3    |
| 1     | 0 1 2 3  | 4 5 6 7    |
| 2     | 0 1 2 3  | 8 9 10 11  |

::motion{path="learn-cuda/global-index"}

写成一般的式子：

```cpp
int i = blockIdx.x * blockDim.x + threadIdx.x;
```

`blockIdx.x * blockDim.x` 是前面这些 block 一共占了多少个位置，再加上 `threadIdx.x`，就是这个线程在整个 grid 里的位置。0 号 block 管 0 到 3，1 号 block 管 4 到 7，2 号 block 接着往后排，首尾相接，一个不漏。

`i` 是 kernel 里的局部变量，每个线程都有自己的一份，互相看不见。同一行代码，不同的线程读到的编号不同，算出来的 `i` 也就不同，各自去算数组里不同的元素。SPMD 管用，靠的就是这一点：同一份程序，靠编号分到不同的数据。

## 多出来的线程：边界检查

`n` 不一定正好是每个 block 线程数的整数倍。比如 `n = 10`、每个 block 4 个线程：要让 10 个元素都有线程算，得开 3 个 block，一共 12 个线程。最后两个线程算出的 `i` 是 10 和 11，可数组里根本没有这两个位置。让它们照样去写，就会写到数组外面，改坏别的数据，甚至让程序崩溃。

所以 kernel 里要加一句 `if`：`i` 小于 `n` 才干活，多出来的线程什么也不做，直接结束。完整的 kernel：

```cpp
__global__ void vecAddKernel(const float* a, const float* b, float* c, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n) {
        c[i] = a[i] + b[i];
    }
}
```

:::warning
漏掉 `if (i < n)` 是新手最常见的错误。`n` 恰好是 256 的倍数时看不出问题，换一个 `n` 就会越界。本课的判题用例会特意取不是 256 倍数的 `n`。
:::

## 启动 kernel：启动配置与向上取整

调用 kernel 和调用普通函数差不多，只是函数名后面多了一段用 `<<<` 和 `>>>` 包起来的**启动配置**：第一个参数是 block 的个数，第二个是每个 block 的线程数。

```cpp
int threads = 256;
int blocks = (n + threads - 1) / threads;
vecAddKernel<<<blocks, threads>>>(d_a, d_b, d_c, n);
```

圆括号里传进去的 `d_a`、`d_b`、`d_c` 是指向显存的指针，数据怎么放进显存，见后面「把数据搬进显存」。

每个 block 的线程数一般定成一个固定值，比如 256；block 的个数要跟着 `n` 算。直接写 `n / threads` 会出问题：C 语言里两个整数相除，小数部分直接扔掉。还是 10 个元素、每个 block 4 个线程，`10 / 4` 得 2，只开 2 个 block、8 个线程，最后两个元素没线程算，结果就错了。所以要**向上取整**，常见写法是先给 `n` 加上 `threads - 1`，再除：

```
(10 + 4 - 1) / 4 = 13 / 4 = 3
```

正好 3 个 block。有了这个式子，每个 block 的线程数可以写死不动，block 的个数自动随着 `n` 变。一百万个元素、每个 block 256 个线程，就开 3907 个 block；多出来的 192 个线程，正好被 kernel 里那句 `if` 挡住。

:::tip
整数相除舍掉小数这件事，在 kernel 里也会碰到。`9 / 5` 两边都是整数，结果是 `1` 而不是 `1.8`。`x * 9 / 5` 没问题：`x` 是 `float`，先算乘法，结果就是 `float`，再除也是浮点除法；但 `9 / 5 * x` 会先算出整数 `1`。要用小数就写成 `9.0f / 5.0f`。
:::

## block 的执行顺序

这些 block 谁先跑、谁后跑，CUDA 不做任何保证：可能按任意次序一个接一个，也可能好几个同时跑。你的代码不能对 block 的顺序做任何假设。

这条规矩换来一个大好处：正因为 block 之间不讲顺序，硬件想同时跑几个就跑几个。小一点的 GPU，同一时刻跑得少，就一批一批往后排；大的 GPU，同时能跑的多得多，一下子就铺开了。同一份程序一行不改，换上更大的 GPU，就自动跑得更快。

## 一个线程算多个元素

上面的写法每个线程算一个元素，但这不是唯一的分法，也可以让一个线程算好几个元素。这时下标公式要重新推，思路和上面一样，把两个问题重新问一遍：

1. 前面每个 block 一共占掉多少个位置？（每个 block 的线程数不变，但每个线程管的元素变多了。）
2. 这个线程管的那几个元素，在自己 block 占的那一段里，从哪儿开始？

推出第一个元素的下标后，后面的每个元素都要单独跟 `n` 比一次：比如每个线程算两个元素、`n` 是奇数时，最后一个线程只有一个元素要算，第二个元素必须被挡住。

分法也不止一种：可以让一个线程取相邻的两个元素，也可以取数组前半段的一个、后半段的一个。只看结果，两种都对；它们在速度上的差别，到「kernel 性能调优」一章讲合并访存时再比较。

## 把数据搬进显存

### 内存和显存

程序要处理的数据，不管是从文件里读的还是从网络上收的，一开始都在 CPU 这边的内存里。GPU 有自己的一块内存，叫**显存**。内存和显存是分开的两块，中间靠一条总线连着，常见的是 PCIe。显存在 CUDA 里的正式名字是 **global memory**（全局内存），为什么叫「全局」，到「共享内存与分块」一章再说。kernel 运行时要读写的数据，都得先放进显存。

### host 端的五步

要让 GPU 算一次向量加法，host 这边要走五步：

1. 在显存里给 `a`、`b`、`c` 分配三块空间。
2. 把 `a` 和 `b` 从内存拷进显存。
3. 启动 kernel，让线程去算。
4. 把算好的 `c` 从显存拷回内存。
5. 释放显存。

第 3 步用上一节的启动配置，其余四步各对应一个 CUDA 提供的函数（API）。

启动 kernel 之后，host 并不会停下来等它算完，而是马上接着往下走。真正停下来等的是第 4 步：拷回要等 kernel 算完才开始。所以拷回来的 `c` 一定是算好的结果。

### 搬数据很贵

来回这么搬要花多少时间？我们在一块 H100 上实测过：`n = 2²⁵`（约 3355 万个元素，每个数组 128 MB），7 次取中位数。

| 做法                         | 耗时      |
| ---------------------------- | --------- |
| CPU 单核跑上面的串行循环     | 37 ms     |
| GPU 把五步走一遍             | 39 ms     |
| 其中：拷进显存               | 29.4 ms   |
| 其中：拷回内存               | 8.1 ms    |
| 其中：kernel 本身            | 0.19 ms   |

GPU 全流程和 CPU 差不多，时间几乎全花在搬数据上；kernel 本身比 CPU 的循环快了将近两百倍。所以实际的程序不会每算一次就来回拷，而是把大块数据一直留在显存里，连着跑好几个 kernel，最后才拷回来。

### 分配和释放：`cudaMalloc`、`cudaFree`

```cpp
float* d_a;
cudaMalloc(&d_a, n * sizeof(float));
// ...
cudaFree(d_a);
```

`cudaMalloc` 故意做得跟 C 的 `malloc` 很像，有两个参数：

- 第二个参数是要多少字节。`n` 个 `float`，每个 4 字节，就是 `n * sizeof(float)`。
- 第一个参数传的不是 `d_a`，而是 **`d_a` 的地址** `&d_a`。C 的 `malloc` 靠返回值把地址交给你，而 `cudaMalloc` 的返回值要留着报告出没出错（见「检查错误」）。所以它换了个办法：你把变量 `d_a` 的地址给它，它把分到的显存地址直接写进 `d_a`。老代码常写成 `cudaMalloc((void**)&d_a, size)`，作用一样，现在不用写这个强制转换了。

`cudaFree` 不用往 `d_a` 里写东西，只要知道地址就够了，所以直接传 `d_a`。

命名习惯：指向内存的指针用 `h_` 开头（host），指向显存的用 `d_` 开头（device），一眼就能分清。

:::warning
`d_a` 里存的是显存地址。在 host 代码里**不能**用 `*d_a` 或 `d_a[i]` 去读它指向的数据：那块地方不在内存里，一读程序就会出错。指向显存的指针只能交给 CUDA 的 API，或者传给 kernel。
:::

### 拷贝：`cudaMemcpy`

第 2 步和第 4 步用同一个函数 `cudaMemcpy`。四个参数依次是：目的地、源头、字节数、方向，**目的地在前，源头在后**。方向用常量写：

| 方向         | 常量                     |
| ------------ | ------------------------ |
| 内存 → 显存  | `cudaMemcpyHostToDevice` |
| 显存 → 内存  | `cudaMemcpyDeviceToHost` |

```cpp
cudaMemcpy(d_a, h_a, size, cudaMemcpyHostToDevice);  // 拷进显存
cudaMemcpy(h_c, d_c, size, cudaMemcpyDeviceToHost);  // 拷回内存
```

### 完整的 host 函数

把五步拼起来：

```cpp
void vecAdd(const float* h_a, const float* h_b, float* h_c, int n) {
    int size = n * sizeof(float);
    float *d_a, *d_b, *d_c;

    // 1. 分配显存
    cudaMalloc(&d_a, size);
    cudaMalloc(&d_b, size);
    cudaMalloc(&d_c, size);

    // 2. 拷进显存
    cudaMemcpy(d_a, h_a, size, cudaMemcpyHostToDevice);
    cudaMemcpy(d_b, h_b, size, cudaMemcpyHostToDevice);

    // 3. 启动 kernel
    int threads = 256;
    int blocks = (n + threads - 1) / threads;
    vecAddKernel<<<blocks, threads>>>(d_a, d_b, d_c, n);

    // 4. 拷回内存
    cudaMemcpy(h_c, d_c, size, cudaMemcpyDeviceToHost);

    // 5. 释放显存
    cudaFree(d_a);
    cudaFree(d_b);
    cudaFree(d_c);
}
```

这个函数的名字和参数类型，跟最开始的串行版本一模一样，调用它的人根本不用知道里面用了 GPU。

:::note
本课的编程题里，`solve` 拿到的指针已经指向显存：分配、拷进、拷回、释放由判题程序替你做好，你只需要写第 3 步，也就是 kernel 和它的启动。
:::

## 检查错误

上面的代码为了看得清楚，省掉了错误检查。实际写程序，这一步省不得。

每个 CUDA API 都返回一个错误码，类型是 `cudaError_t`。成功是 `cudaSuccess`；不成功，就该把出错原因打印出来。比如显存不够时，`cudaMalloc` 就会失败：

```cpp
cudaError_t err = cudaMalloc(&d_a, size);
if (err != cudaSuccess) {
    printf("%s\n", cudaGetErrorString(err));
}
```

启动 kernel 不一样，它没有返回值。比如每个 block 要了 2000 个线程，超过了 1024 的上限，启动就会失败，可它不会自己报错，程序照样往下跑，最后拿回一堆错的结果。所以启动之后要紧跟着调用 `cudaGetLastError()`，问一句刚才出没出错：

```cpp
vecAddKernel<<<blocks, threads>>>(d_a, d_b, d_c, n);
cudaError_t err = cudaGetLastError();
if (err != cudaSuccess) {
    printf("%s\n", cudaGetErrorString(err));
}
```

实际项目里，常把这些检查写成一个宏，每个调用都套上。

## 编译：nvcc

一个 `.cu` 文件里混着两种代码，一种在 CPU 上跑，一种在 GPU 上跑，还有 `__global__` 这样的关键字和 `<<<>>>` 这样的新语法，普通的 C++ 编译器不认识。所以要用 CUDA 自带的编译器 **nvcc**：

1. nvcc 先按关键字把文件拆成两半。
2. host 那一半交给系统里普通的 C++ 编译器，编成 CPU 的机器码。
3. device 那一半 nvcc 自己编，编成 GPU 的机器码，同时还留一份 **PTX**（GPU 的一种中间代码）。
4. 两半编出来的东西，一起装进最后的程序。

运行时，驱动挑出跟这块 GPU 匹配的机器码来用。要是换上了一块更新的 GPU，程序里没有跟它匹配的机器码，驱动就把 PTX 现场编译一遍。

## 三个函数限定符

| 限定符       | 在哪儿执行 | 谁能调用                          | 说明                                     |
| ------------ | ---------- | --------------------------------- | ---------------------------------------- |
| `__global__` | device     | host                              | kernel；每调用一次，就开出一个新的 grid  |
| `__device__` | device     | kernel 或别的 `__device__` 函数   | 普通函数调用，不开新线程；host 调用不了  |
| `__host__`   | host       | host                              | 普通 CPU 函数；什么都不写，默认就是它    |

`__host__` 和 `__device__` 可以一起写，编译器会编出两个版本，CPU 和 GPU 都能调用。

## 小结

本章用到的 CUDA 扩展一共就四类：

1. 函数限定符：`__global__`、`__device__`、`__host__`。
2. 启动 kernel 的 `<<<blocks, threads>>>`。
3. 预先设好的变量：`threadIdx`、`blockIdx`、`blockDim`。
4. 管显存、搬数据的 API：`cudaMalloc`、`cudaMemcpy`、`cudaFree`，以及错误检查用的 `cudaGetLastError`。

本章只学了够用的一小部分，别的功能后面用到再讲。真正的重点是背后的并行思路：**写 kernel，就是只写一个线程要干的活，也就是原来循环里的一次迭代。** 整个循环换成一大批线程，大家跑的都是同一份 kernel，每个线程靠自己的编号找到自己的元素，再用 `if` 挡住多出来的线程。
